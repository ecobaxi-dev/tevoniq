**التاريخ:** 13 نوفمبر 2026 — توقيت إسطنبول.
**القرار:** REQUEST CHANGES — إصلاح نقاط التوفّر والخصوصية واستكمال نشر صفحة الإعلان قبل إطلاق الحملة.
**الثقة:** مرتفعة في النتائج المعاد إنتاجها محليًا وحالات HTTP المسجلة؛ متوسطة في ربط الأعراض العامة بإعداد الاستضافة، لعدم الوصول إلى سجلات الإنتاج وحساباته.

## 1. نطاق المراجعة وحدودها

راجعت الحالة الحالية للمستودع عند `133b347ac45fbf9768c787839478f86522af5e97` **مع تغييرات صفحة الإعلان غير الملتزمة الموجودة في مساحة العمل**، والموقع المنشور `https://www.tevoniq.com`. الكود المحلي والمنشور ليسا بالضرورة النسخة نفسها؛ صفحة الإعلان مثال مثبت على ذلك.

شملت المراجعة:

- المصادقة والجلسات واستعادة كلمة المرور والصلاحيات ووسيط CMS.
- التواصل وعرض السعر والنشرة والوظائف ورفع الملفات والصور.
- مسارات تسجيل بيستو والتحقق والتجربة وتفعيل الشراء وتسليم البريد، دون إصدار تراخيص فعلية.
- منع حقن المدخلات والمسارات، ترويسات الحماية، الأسرار، الاعتماديات، إعداد النشر والتتبع والموافقة.
- الصفحات العامة والخدمات والنماذج التوضيحية والبحث وSEO وتجربة الهاتف والإتاحة.
- الاختبارات الآلية الموجودة، مع إعادة إنتاج مستقلة لحد الطلبات وخصوصية النموذج وفروق البناء.

لم أعدّل كود التطبيق أو إعدادات الإنتاج أو سجلات CMS، ولم أرسل رسائل أو طلبات شراء أو نماذج إلى الموقع المنشور. الاختبارات التي تغيّر حالة استخدمت محاكيات وبيانات محلية. فحص الإنتاج كان قراءة فقط، باتصالين متزامنين في جولة HTTP الأساسية. لم أختبر قدرة الخادم على تحمّل الضغط أو أصل إلى قاعدة الإنتاج أو حسابات Render/Cloudflare/البريد/الإعلانات. ليست هذه شهادة بخلو كل المسارات من الثغرات، أو فحصًا للشبكة ونظام تشغيل الاستضافة.

بيئة التنفيذ المحلية: Node `22.21.1` وnpm `11.3.0`. المشروع يطلب Node `24.x`؛ لذا يلزم تشغيل بوابة الإصدار النهائية على Node 24 أيضًا. لم أغيّر إصدار Node أو الاعتماديات.

### SEC-01 — حصص الطلبات مشتركة بين زوار الواجهة

**المشكلة:** وسيط Web يتصل بـAPI عبر `127.0.0.1`. المحدد العام في `main.ts` يستخدم مفتاح IP الافتراضي وبحد 120 طلبًا في الدقيقة، دون مفتاح يعتمد هوية العميل الموثقة. إضافة الترويسات الموقّعة المستخدمة في بقية التطبيق لا تغيّر مفتاح هذا المحدد العام.

**الإثبات المحلي:** استُخدم API محلي وقاعدة اختبار غير متاحة، ومسار health فقط. بعد 120 استجابة ناجحة لهوية عميل منطقية أولى، أعاد الطلب الأول لهوية ثانية مختلفة **429**، رغم إرسال IP وتوقيع HMAC صحيح مختلف لكل منهما. لم يُنفّذ هذا الاختبار العددي على الإنتاج.

**الأثر:** الزيارات أو جلب صفحات كثيرة قد تستهلك حصة الجميع؛ وقد تتأثر صفحات المحتوى والإدارة والنماذج في الوقت نفسه. توجد مشكلة أضيق إضافية إذا لم تضبط هوية العميل أصلًا: `submissionIp` يرجع إلى IP الوسيط، فيشترك الزوار في حدود النماذج 10/15 دقيقة وحدود المصادقة. لا يثبت الفحص الحالي هل أسرار وترويسات ingress مضبوطة في حساب الإنتاج.

**علاقة أعراض الإنتاج:** الردود العابرة 500 وغياب أوصاف SEO ثم عودتها يتوافقان مع احتمال إخفاق API، لكن لم تتوفر سجلات تسمح بإثبات أن المحدد هو سبب كل استجابة بعينها. لا يُفترض أن الصفحات الثلاث معطلة دائمًا.

**الإصلاح المقترح:**

1. اعتماد هوية العميل من ingress يكتب الترويسة بنفسه، ثم التحقق بالتوقيع قبل استخدامها في مفتاح المحدد. لا تثق بـ`X-Forwarded-For` المرسل عشوائيًا، ولا تفعّل `trust proxy=true` دون تحديد حدود الثقة.
2. التعامل الصحيح مع IPv6 باستخدام آلية المفاتيح المناسبة في المكتبة.
3. فصل حدود القراءة العامة عن تسجيل الدخول والإرسال، ووضع سياسة خاصة للفحوص الصحية. إبقاء حماية إجمالية محسوبة للسعة بدل إزالة الحماية كلها.
4. اختبار المسار كاملًا من المتصفح إلى BFF ثم API، بما فيه سقوط الترويسة أو توقيع غير صالح.

**معيار القبول:** بلوغ العميل A الحد لا يحجب العميل B. الترويسات المزورة لا تمنح حصصًا جديدة. اجتياز زحف منخفض التزامن دون 500 أو تغيّر بيانات SEO بسبب الحدود.

تصف وثائق [express-rate-limit](https://express-rate-limit.github.io/ERR_ERL_UNEXPECTED_X_FORWARDED_FOR/) هذا النمط من الحدود العامة خلف الوسطاء.

### SEC-02 — Turnstile معطّل في نموذج التواصل المنشور

**الإثبات:** بيانات نموذج `/ar/contact` المنشور احتوت `turnstileSiteKey: null`. وملف Render الملتزم يحدد `TURNSTILE_MODE=disabled`. `LeadBotProtection.verify` يتجاوز التحقق عندما لا يكون الوضع `turnstile`.

**الأثر:** إرسال آلي ورسائل غير مرغوبة واستهلاك حصة البريد/قاعدة البيانات. توجد بالفعل مصيدة حقول وحدود إرسال؛ غياب Turnstile لا يعني أن النموذج بلا حماية، ولا يثبت حصول إساءة فعلية.

**الإصلاح:** إنشاء مفاتيح صحيحة للنطاقات، وتفعيل الوضع في الاستضافة، ثم التحقق من تطابق action وhostname وانتهاء الرمز. لا تضمّن المفتاح السري في الواجهة. صحّح SEC-01 بالتوازي حتى لا تعاقب حدود مكافحة الإساءة الزوار الحقيقيين.

**معيار القبول:** الطلب بلا رمز أو برمز خاطئ/لنطاق آخر مرفوض، والطلب الصحيح يُحفظ مرة واحدة. راجع إمكانية استخدام النموذج على الهاتف وإتاحة مسار تواصل بديل.

### SEC-03 — بريد النشرة يظهر في URL إذا لم يعمل JavaScript

**الإثبات:** `.footer-newsletter-form` لا تحدد `method` أو action آمنًا. عند تعطيل JavaScript في المتصفح المحلي، أدى إرسال عنوان اختبار إلى طلب تنقل **GET** يحتوي البريد في query. لم يُرسل عنوان اختبار إلى الموقع المنشور.

**الأثر:** ظهور البريد والموافقة في سجل المتصفح وربما سجلات الوسطاء، إضافة إلى أن الاشتراك لا يصل إلى نقطة الإرسال الصحيحة. نجاح مسار React المعتاد لا يعالج سلوك HTML الافتراضي.

**الإصلاح:** تحديد POST صراحةً وإما توفير معالج خادمي مناسب لصيغة النموذج، أو منع الإرسال الأصلي بأمان حتى التهيئة مع رسالة noscript واضحة. تغيير `method` وحده مع الإرسال إلى مسار لا يفهم الصيغة ليس إصلاحًا وظيفيًا كاملًا. راجع نماذج CMS الأخرى أيضًا كتحسين دفاعي؛ لم يُثبت تسرب كلمة مرور منها في هذه الجولة، إذ بعضها لا يظهر أصلًا قبل التهيئة.

**معيار القبول:** مع JavaScript وبدونه، أو عند تعذّر تحميل الحزم، لا يظهر البريد أو أي بيانات نموذج في URL. الاشتراك ينجح فعليًا أو تظهر رسالة بديلة مفهومة.

مرجع الأثر: [OWASP — بيانات حساسة داخل query strings](https://community.owasp.org/vulnerabilities/Information_exposure_through_query_strings_in_url).

### REL-01 — صفحة الإعلان موجودة محليًا وغير منشورة

**الإثبات:** المساران `/ar/start` و`/en/start` يعيدان 404 في إعادة الفحص، بينما مسارهما موجود ويُبنى محليًا. تعديلات الواجهة والتحقق المشترك غير ملتزمة في Git وقت المراجعة. ترويسة CSP المنشورة لا تتضمن إضافات Google Ads الموجودة في النسخة المحلية أيضًا؛ دليل إضافي على اختلاف النشر، لا ثغرة مستقلة.

**الأثر:** إرسال الإعلان إلى الرابط الآن لا يصل إلى صفحة استقبال العملاء المطلوبة.

**الإصلاح:** بعد معالجة نقاط المنع، نشر Web وAPI مع حزمة validation المشتركة وإعدادات التحليلات الصحيحة. لا تنشر الواجهة وحدها لأن التحقق القديم من مصدر الطلب قد يرفض `/ar/start`. لا حاجة مثبتة إلى migration جديدة لهذا التغيير.

**معيار القبول:** GET للمسارين 200 على نطاق الإنتاج، اختبار طلب حقيقي واحد مصرح به يصل إلى لوحة العملاء وإشعارات البريد، ثم تحقق Meta Test Events وGoogle Tag Assistant من عدم تكرار التحويل. لم أنفّذ طلب الإنتاج الحقيقي ضمن هذه المراجعة.

### FUN-01 — النشرة قد تبدو متاحة رغم تعطيل إرسال البريد

**الحالة المسببة:** `EMAIL_TRANSPORT=disabled` أو transport غير قادر فعليًا على الإرسال.

**الدليل من الكود:** `/newsletter/config` يرجع مفتاح Turnstile فقط. `SiteFooter` يعتبر وجود استجابة الإعدادات كافيًا لـavailable. نقطة subscribe تقبل الطلب وتنشئ عمل التأكيد؛ العامل يستبعد أعمال CONFIRM عندما `confirmationEnabled=false`. وبالتالي يمكن إظهار نجاح للمستخدم مع بقاء التأكيد معلقًا. هذا سلوك مشروط مثبت من المسار؛ لم أُثبت أن بريد الإنتاج معطل حاليًا.

**الإصلاح:** إرجاع حالة إرسال موثوقة في config، ومنع/توضيح الاشتراكات الجديدة عند التعطيل حسب قرار المنتج، مع الحفاظ على تأكيد/إلغاء اشتراك سابق حيث يلزم. عرض حالة طابور البريد في الإدارة والتنبيه إلى التأخر والفشل، واختبار ضبط المزود فعليًا.

**معيار القبول:** عند التعطيل لا تعد الواجهة بوصول رسالة لن تُرسل؛ وعند التفعيل تنتهي دورة pending → confirmation email → active. لا يُكشف وجود عنوان بريد بعينه.

### UX-01 — تباين منخفض في صفحة الإعلان

**الإثبات:** مسح axe الموجّه على `/ar/start` سجل مخالفة color-contrast، منها:

- `#778775` فوق الأبيض في عبارة WORKSPACE: نسبة 3.81:1 لنص 10px.
- `#71816e` فوق الأبيض في حالة داخل التصوّر: 4.14:1 لنص 10px.
- `#7a8974` فوق الأبيض في ترقيم بطاقات الخدمات: 3.71:1 لنص 12px.

**الإصلاح:** تغميق درجات النصوص الصغيرة وفحص جميع العقد، لا الاقتصار على الأمثلة الثلاثة. لا يكفي إخفاء نص مفهوم عن قارئ الشاشة لتجاوز اختبار التباين. أعد القياس على بناء النشر والهاتف والكمبيوتر.

**معيار القبول:** اجتياز axe للفئة المناسبة، وتباين 4.5:1 للنص العادي محل المخالفة، مع مراجعة بصرية. هذه نتيجة في الصفحة المحلية الجديدة، وليست ادعاء بوجودها على صفحة إعلان منشورة.

### PERF-01 — تحميل كامل البيانات في البحث الإداري

**الدليل:** `AdminController.search` يستدعي findMany دون take على عدة جداول ثم يفلتر ويرتب ويقص النتائج في ذاكرة Node؛ ومن ذلك كامل مقالات المحتوى وترجماته. `trash` يجلب كذلك كل السجلات المؤرشفة قبل الترقيم.

**الأثر:** استهلاك ذاكرة ووقت ونقل من قاعدة البيانات يزداد مع البيانات، خاصة في استضافة صغيرة. الوصول إلى هذه المسارات محمي؛ لم يثبت توقف الخادم الحالي أو استغلال عام لها.

**الإصلاح:** نقل البحث والتصفية وحدود النتائج إلى SQL، وتحديد select للأعمدة اللازمة. عند دمج جداول متعددة استعمل فهرسًا/استعلامًا موحدًا أو حدودًا مدروسة لكل نوع، واحسب total باستعلامات منفصلة. لا تعتمد فقط على slice بعد التحميل.

**معيار القبول:** اختبارات ببيانات كبيرة تؤكد ثبات حدود السجلات المحمّلة وحجم الاستجابة والذاكرة، مع صحة البحث والترقيم.

### BUILD-01 — اختلاف نتائج الهاتف بين بنائي Web

**الإثبات:** بناء webpack نجح تقنيًا، لكن 20/110 حالة تصفح فشلت بسبب العرض الأفقي. القياس الموجّه حدد ترويسة `.site-header-actions` كعنصر متجاوز: صفحة عربية بعرض نافذة 390 بلغ scrollWidth فيها 435، والإنجليزية نحو 438؛ في 320 بقي المحتوى المتجاوز بالعرض نفسه. إعادة الحالات العشرين على **Turbopack الافتراضي نجحت كلها** دون تعديل الكود. عينة الصفحة العربية المنشورة قاست 390/390 ولم تُظهر هذا التجاوز.

**الاستنتاج:** المشكلة خاصة بسلوك CSS في البناء البديل المختبر؛ ليست 20 عطلًا مستقلًا، ولا يصح وصف الهاتف المنشور بأنه مكسور. يبدو أن ترتيب قواعد CSS/حزم الواجهة هو الاتجاه الأول للتحقيق، ويجب تأكيد القاعدة الفائزة قبل التعديل.

**الإصلاح:** تثبيت مسار البناء المدعوم وإجراء E2E على ناتجه نفسه. إن أردنا دعم webpack، فلتكن قواعد ترويسة الهاتف صريحة ومستقرة أمام ترتيب الاستيراد؛ لا تخفِ overflow على body لإخفاء أزرار خرجت من الشاشة.

**معيار القبول:** توثيق بناء النشر، واختبارات 320 و390 و1440 بكسل. إن بقي webpack مدعومًا، اجتياز الحالات العشرين عليه أيضًا.

### DEP-01 — تنبيه في أدوات التطوير

**الإثبات:** npm سجل 8 تنبيهات متوسطة في الشجرة الكاملة، مصدرها minimatch وتنقلها عبر typescript-eslint وeslint-config-next. سجل الإنتاج خالٍ من التنبيهات وقت الفحص.

**الأثر:** مخاطر في بيئة الأدوات عند معالجة أنماط غير موثوقة؛ لا يوجد دليل هنا على إمكانية استغلالها من زائر للموقع. العدد 8 يصف حزمًا متأثرة في الشجرة وليس 8 مصادر مستقلة.

**الإصلاح:** تحديثات متوافقة للأدوات وفحص lockfile ثم typecheck وlint والبناء والاختبارات. لا تنفذ `npm audit fix --force` عشوائيًا؛ الاقتراح الحالي يتضمن تخفيضات/تغييرات رئيسية غير مناسبة بالضرورة. شغّل المسار النهائي على Node 24 كما يطلب المشروع.

المصدر الأولي: [تنبيه minimatch](https://github.com/advisories/GHSA-g3hv-75wg-m249).

## 4. ضوابط الحماية التي لم تُظهر الفحوص خللًا فيها

- الجلسات تستخدم رمزًا عشوائيًا، وتُخزن بصمته في قاعدة البيانات. كوكي CMS في BFF هي HttpOnly وSameSite=Strict وتُضبط Secure عند HTTPS، ولا يعاد الرمز إلى JavaScript بعد تسجيل الدخول عبر BFF.
- الحارس العام يرفض مسارات الإدارة بلا مصادقة وسياسة صلاحيات معروفة. توجد إصدارات مصادقة وإبطال للجلسات وحد خمول، وفحص Origin لكتابات BFF.
- اختبارات المصادقة ورفض الكتابة عبر Origin مختلف وخصوصية بيانات بيستو واجتياز حالات انتهاء الجلسة نجحت في المحاكاة. لم تُستخدم حسابات إدارة إنتاجية.
- المسارات التي روجعت تستخدم تحقق Zod واستعلامات بمعاملات، مع ضبط أطوال المدخلات. رسم المحتوى المنظم وJSON-LD يتضمن تهريبًا مناسبًا في المسارات المراجعة.
- رفع الصور يقيّد النوع والأبعاد وحجم الإدخال، وSVG يُعاد بناؤه بقائمة سماح. مرفقات العملاء وCV تُسلّم عبر مسارات إدارية، ورفع CV في الإنتاج يرفض عند غياب الفاحص بدل قبوله دون فحص.
- ملفات `.env` الفعلية غير متتبعة في Git. فحص HEAD لـ`/.env` و`/.git/config` المنشورين أعاد 404. لم تُقرأ محتويات حساسة من الخادم.
- CSP بتوقيع nonce وHSTS وnosniff ومنع الإطارات وسياسة إحالة موجودة في العينة المنشورة.
- اختبارات الخدمات المتقاعدة نجحت في منع إعادة ظهورها من سجلات CMS قديمة، مع الحفاظ على المسارات التركية القائمة وفق سياسة المشروع.
- دورة بيستو تتضمن تحقق البريد وربط التسجيل بالجهاز وتوقيع الرخص ومعاملات تحمي التفعيل من التعارض. نجاح الاختبارات لا يثبت جاهزية برنامج Windows أو مفاتيح الإنتاج أو تسليم الترخيص فعليًا؛ لا تُفعّل التحميل لمجرد هذه المراجعة.
- التتبع مقيّد بفئات الموافقة في الكود، وحدث العميل المحتمل مرتبط بالاستلام الناجح. اختبار GA4 المعزول نجح؛ لم يُتحقق من إعداد حسابات الإعلانات أو الحاويات الحقيقية.

لم أثبت في هذه الجولة ثغرة حرجة، أو تجاوز مصادقة، أو SQL injection، أو كشف ملفات سرية من الإنتاج. هذه صياغة لنتيجة الفحص، لا ضمان عدم وجودها.

## 6. ترتيب الإصلاح المقترح ومعايير انتهاء كل مرحلة

### المرحلة الأولى — التوفّر والخصوصية

**شرط الإغلاق:** نتائج إعادة إنتاج مثبتة للحصص والنماذج، ورفض إساءة الإرسال دون تعطيل الزوار الحقيقيين.

**شرط الإغلاق:** بناء واختبارات على Node 24 ومسار النشر نفسه، مع مراجعة نتائج الإنتاج وسجلاته بعد النشر.
