# Purchase activation backend — disabled by default

This phase prepares the API, central ledger and automatic operating-permit email.
It does not collect payment, issue a real purchase, publish installers, change the
development restaurant's trial or enforce sales. Company/customer entry screens and
the Windows import flow are the next phase; keep both new flags false meanwhile.

## Company purchase issuance

Authenticated CMS `SUPER_ADMIN`/`ADMIN` accounts with `settings.update` may call:

- `POST /api/v1/cms/pesto/purchases`: strict `{ requestId, email, reference }`.
- `POST /api/v1/cms/pesto/purchases/:id/revoke`: revoke an unused key only.

`requestId` is a UUID idempotency key. The email must already belong to a verified
Pesto customer. A sale/payment is checked by the company before issuance; the free
public endpoint cannot create purchase keys. The reference and issuer actor are
retained for audit. Reusing a request with different details is rejected. Keys are
not sold/generated by the public registration UI.

The authorized issue response contains `{ purchaseId, purchaseKey, email }`. It is
sensitive, no-store, and must never be put in browser persistent storage, telemetry,
URLs or logs. A future company UI should show/copy it only to an authorized operator.
The application request logger deliberately omits bodies/query/credentials.

The key format is `PSTO-` plus 64 uppercase hexadecimal characters. The secret part
is an HMAC-SHA256 result using the API-only registration email key, an independent
purchase purpose, purchase UUID and random nonce. The database stores only its hash
and nonce, not the raw key. This allows an authenticated lost-response retry to
recover the same key without storing it in plaintext. Key rotation must preserve
the original issuer/email material and be designed separately; mismatched derivation
is rejected rather than silently rotating/reissuing keys.

## Customer redemption and signed permit

The customer obtains a fresh email-verification ticket for the target installation.
The ticket consumed by an earlier trial cannot be reused for a purchase. The new
`POST /api/pesto/registrations/activate` proxy sends strict
`{ registrationTicket, installationId, deviceHash, purchaseKey }` to the private API.
Only the company-preconfigured HTTPS proxy target and authenticated edge-IP contract
are used. Activation is rate-limited; body fields cannot set owner, dates or limits.

Within a serializable transaction, the purchase must belong to the verified
ticket's customer, be unrevoked, and match the bound installation/device. Proof
consumption, purchase consumption, the immutable signed perpetual license, retry
grant and email outbox entry commit together. Activation and revocation contend
on the same purchase row. Unique constraints enforce one license per purchase,
installation and device. A mismatch requires a separate support/device-transfer
workflow; no reset/rebind is supplied here.

When upgrading a trial, the original trial's `registrationId` is retained in the
signed perpetual permit because the Windows store already pins that registration.
Trial dates and signed trial bytes remain untouched. The new permit retains the
v1 format and two users/two concurrent devices, has `kind=perpetual` and a null
expiry. Maintenance entitlement remains separate and no recurring internet check
is introduced.

The reply `{ activationId, status: 'email-queued' }` is an acknowledgement, not a
delivery confirmation or the permit itself. The same committed request can be
retried for 15 minutes; a fresh verified ticket for the same owner/key/device
returns the original activation without extending dates or duplicating the outbox.
It does not resend a previously sent message. Company-controlled resend/recovery
with an audit trail remains pending.

## Automatic email

The API-only worker leases a durable outbox row, verifies the stored signature and
license/device claims, and sends the operating permit to the stored verified email.
It never accepts an address in the activation request. Arabic/English/Turkish mail
uses the navy/gold identity and includes an LTR copyable permit, support and a plain
text fallback. Dynamic content is escaped. No purchase key or private signing key
appears in the operating mail. The permit is public signed claims bound to a device,
not a portable private key.

At most five attempts, including crashed claims, are allowed. Old leases can be
reclaimed; success/failure updates require the current lease. Errors use fixed
nonsecret text. The mail ID is stable for provider deduplication. SMTP has no
universal exactly-once guarantee if the process crashes after provider acceptance;
provider idempotency is bounded by its retention policy. After exhausted attempts,
the company must inspect the failure; no infinite automatic resend occurs.

## Deployment gate and database

- Private API: `PESTO_PURCHASE_ENABLED=false` by default.
- Public web proxy: `PESTO_PUBLIC_PURCHASE_ENABLED=false` by default, in addition to
  the existing enrollment flag.
- Enabling requires registration, mail delivery and the dedicated valid P-256
  signer/email key. No new production keys are generated.
- Migration `20261025000100_pesto_purchase` adds four isolated licensing tables;
  it does not modify restaurant data or delete existing trial records.

Do not enable either flag until company issuance UI, customer verification/purchase
entry, email permit import and recovery have been tested together. Public download
buttons still link to the informational downloads section.

## Validation

`tests/pesto-purchase.test.mjs` covers strict schemas, purpose-separated purchase
keys, perpetual signatures and localized mail escaping. Run after the API build.
`tests/pesto-purchase.integration.mjs` migrates an embedded PostgreSQL database and
uses ephemeral signers/fake email, exercising issue retries, hashed keys, owner
verification, transaction rollback, trial-to-perpetual pin preservation, immutable
activation recovery, device-change rejection, key revocation, worker leasing,
failure/crash limits, signature rejection, authenticated HTTP and proxy/rate gates.
It never loads `.env`, touches production, or sends email. Its pool has one
connection; it is not a multi-session production PostgreSQL stress test.

Set `PESTO_DOTNET_INTEROP_PROJECT` to the RestaurantOS LicensingInteropChecks project
to validate a public synthetic Node-issued permit in the real .NET verifier,
including perpetual access twenty years later, wrong-device and tamper rejection.
Existing trial/registration/proxy integration checks remain regression requirements.
Real mail-client rendering and customer end-to-end purchase/import remain pending.
