# تشغيل TEVONIQ على الخادم المنزلي

الهدف تجربة `https://home-test.tevoniq.com` دون تحويل النطاق الأساسي. ملف `compose.home.yaml` مستقل عن ملف التطوير ويستخدم اسم المشروع نفسه `tevoniq` وخدماته، وvolume الموجود `tevoniq_postgres_data` بوصفه external. يرفض Docker إنشاء volume بديل فارغ إن لم يوجد الأصلي. لا تستخدم اسم مشروع آخر ولا `down -v` ولا تغيّر POSTGRES_* عند الانتقال.

## المرحلة الأولى: نسخة من القاعدة الحالية

على Ubuntu داخل مجلد المشروع:

```bash
git pull --ff-only
sudo env BACKUP_DIR=/home/tevoniq/backups/tevoniq bash scripts/home/backup.sh
```

هذه نسخة PostgreSQL فقط تشمل الحسابات والطلبات الموجودة محليًا. الأداة لا تحذف نسخًا قديمة، وتتخلص من الملف المؤقت إذا فشل pg_dump. يحفظها root بصلاحيات مقيدة، لذا قد تحتاج sudo لنسخها. انقل نسخة مشفرة إلى جهاز آخر أو تخزين مستقل بعد التأكد منها؛ النسخة على القرص نفسه لا تحمي من تلفه. لا ترفعها إلى Git ولا تشارك محتواها. لا تعني سلامة ترويسة الملف نجاح الاستعادة؛ اختبر الاستعادة في قاعدة منفصلة قبل التحويل النهائي. أي ملفات مرفوعة إلى volume الإعلام المحلي تحتاج نسخة مستقلة أيضًا. لا تحذف volume الإعلام القديم عند تعطيل الرفع.

## إعداد الإنتاج، دون تشغيله بعد

احتفظ بملف `.env` الحالي كما هو. انسخ `.env.home.example` إلى `.env.home` مرة واحدة بصلاحيات 600، ثم املأ القيم من إعدادات الخدمات مباشرة دون إرسالها في المحادثة. الملف الحقيقي مستبعد من Git. استخدم:

- SITE_URL: النطاق التجريبي HTTPS دون شرطة أخيرة.
- EMAIL_FROM وRESEND_API_KEY: المرسل المتحقق ومفتاح Resend الخاص.
- TURNSTILE_SITE_KEY وTURNSTILE_SECRET_KEY: المفاتيح الحقيقية، مع إضافة النطاق التجريبي في Cloudflare وفي TURNSTILE_HOSTNAMES.
- LEAD_PROXY_SECRET: سلسلة عشوائية من `openssl rand -hex 32`، مستخدمة في الويب والـAPI.

لا تنسخ بيانات اتصال Neon إلى هذا الملف. تستخدم الخدمات PostgreSQL المحلي داخل شبكة Docker خاصة. MEDIA_STORAGE=disabled مؤقتًا، لذلك لا يُعد هذا الإعداد حلًا لتفعيل رفع الوسائط أو CV. يمكن استكمال تخزين S3 والفحص قبل تفعيل تلك الوظائف. لا تغيّر حالات توفر منتجات Pesto أو مفاتيحها ضمن نقل الاستضافة.

## التحقق على Ubuntu

بعد إنشاء `.env.home` وإعادة بناء صورة أدوات التهيئة بالنسخة الجديدة:

```bash
sudo docker compose --profile app build migrate
sudo docker compose --profile app run --rm --no-deps --workdir /app \
  -v "$PWD/.env:/run/database.env:ro" -v "$PWD/.env.home:/run/home.env:ro" \
  migrate node scripts/home/check-env.mjs /run/database.env /run/home.env
sudo docker compose --env-file .env --env-file .env.home -f compose.home.yaml --profile tools config --quiet
sudo docker volume inspect tevoniq_postgres_data --format '{{.Name}}'
```

`config --quiet` مهم لتجنب طباعة الأسرار. فحوص الإعدادات لا تختبر صلاحية مفاتيح الخدمات أو استلام البريد. لم يتوفر Docker CLI في بيئة التأليف؛ يلزم هذا التحقق على جهاز Ubuntu قبل التطبيق، ثم اختبار الصحة والخدمات فعليًا.

## قبل التحويل إلى إعداد الإنتاج

1. تحقق من نسخة احتياطية ووسيلة رجوع إلى إعداد التطوير والبيانات نفسها.
2. جهز Cloudflare Tunnel دائمًا إلى `http://localhost:3000` على Ubuntu دون فتح منافذ المودم، وأضف النطاق التجريبي فقط. لا تستخدم Quick Tunnel عشوائيًا للإنتاج.
3. تحقق من Turnstile وResend والنطاق والمصادقة، ثم نفذ migrations المحلية قبل تشغيل الإصدار الجديد. لا تشغل bootstrap أو seed على قاعدة مُعدّة بالفعل.
4. بعد نجاح فحوص الإعدادات، تشغيل خدمات compose.home يعيد إنشاء الحاويات مع إبقاء volume. لذلك ينفذ في نافذة صيانة بعد حفظ النسخة وليس بمجرد تنزيل الملف.
5. لا تخلط ملفي التشغيل في أمر `-f` واحد. استخدم compose.home وحده مع ملفي البيئة عند تشغيل الإنتاج، وcompose.yaml وحده عند العودة للتطوير.
6. لا تنشر الـAPI أو PostgreSQL. المنفذ الوحيد على المضيف هو `127.0.0.1:3000`، وcloudflared يعمل على المضيف. ترويسة cf-connecting-ip موثوقة فقط لأن المسار العام يمر بالنفق ولا توجد خدمة ويب منشورة مباشرة على الإنترنت.

تحتوي إعدادات الإنتاج على restart تلقائي وحدود للسجلات والذاكرة. استخدام HTTPS مطلوب لتجربة جلسة الإدارة في الإنتاج؛ لا تعتمد على عنوان localhost HTTP بعد التحويل. راقب صفحة الصحة والدخول والطلبات والبريد والروابط والتنزيلات على النطاق التجريبي.

## تجهيز الجهاز المستمر

تظل إدارة SSH داخل الشبكة المنزلية. اضبط حجز DHCP للعنوان وتفضيل Ethernet إن توفر. قبل استخدام UFW، أضف سماح SSH للشبكة الموثوقة وتحقق من جلسة ثانية حتى لا تفقد الوصول. احتفظ بإمكانية الوصول الفعلي للجهاز. اضبط منع السكون وسلوك غطاء اللابتوب والتحديثات والنسخ المجدولة في خطوات منفصلة بعد الاختبار، مع تهوية مناسبة وبقاء الجهاز متصلًا بالطاقة. تشغيل Windows بدل Ubuntu يوقف الاستضافة.

لا تُلغِ Render ولا تحذف Neon قبل نقل البيانات الحالية والتحقق منها واتخاذ قرار التحويل النهائي. نجاح النسخة المحلية لا يعني أن بيانات Neon الأخيرة موجودة فيها.
